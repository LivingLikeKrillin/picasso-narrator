# 경계 — narrator 가 무엇이고 무엇이 아닌가

- 작성 2026-09-17 · `picasso-narrator` 저장소의 첫 문서
- 짝: `picasso` 저장소의 `ADR 40`(번들과 대안을 계약이 아닌 조회 결과로 둔다)

> 이 문서를 먼저 쓴다. 코드보다 경계가 먼저 정해져야 하고, 나중에 쓰면 이미 넘은 선을 정당화하는 문서가 된다.

---

## 1. 무엇인가

**사건 번들을 읽어 원인 설명과 검증된 근거 인용을 내놓는 층.** picasso 의 소비자이며, picasso 는 이 저장소의 존재를 모른다.

| 한다 | 내용 |
|---|---|
| 번역 | 번들의 사실을 운영자가 읽을 문장으로. **판정이 아니라 번역이다** |
| 근거 검색과 인용 | 코퍼스에서 관련 문서를 찾아 붙인다. 인용의 검증은 Nexus 가 한다 |
| 후보 원인의 정렬 | 번들만으로 원인이 하나로 좁혀지지 않을 때. **이것만이 실질 판단이고, 제안이지 판정이 아니다** |

| 하지 않는다 | 이유 |
|---|---|
| 상태 판정 | 결정적 층의 몫. 번들이 이미 판정을 담고 있다 |
| 대안 생성 | 탐색기의 몫. 여기는 탐색 결과를 설명한다 |
| 실행·승인 | 승인 경로의 몫 |
| 알림 등급 결정 | 판정이 등급을 정하고, 여기는 그 알림에 실릴 문장만 쓴다 |
| 감시·탐지 | 직접 보면 탐지를 중복 구현하게 되고 같은 사건에 두 개의 진실이 생긴다 |

---

## 1.5 구성 — 네 조각, LLM 은 하나

이 저장소는 그릇이다. 안에 조각이 넷이고 **LLM 이 들어가는 것은 하나뿐이다.**

| 조각 | 하는 일 | LLM |
|---|---|---|
| **수신기** (`receiver`) | 새 번들이 생겼는지 보고 집어온다. 멱등 처리, 재시도, 실패 기록 | 없음 |
| **질의 구성** (`composer`) | 번들의 필드에서 검색 질의와 입력을 만든다 | 없음 |
| **설명 생성** (`explainer`) | Nexus 에 질문을 던지고 답과 인용을 받는다 | **여기만** |
| **기록기** (`recorder`) | 설명과 인용, 또는 「근거 없음」, 또는 「생성 실패」를 사건에 붙인다 | 없음 |

**용어를 섞지 않는다.** "번들을 인지한다" 는 수신기가 하는 일이고, 설명 생성과는 다른 조각이다. 이 구분이 흐려지면 "에이전트가 늦게 알면 대응이 늦어진다" 같은 오해가 생긴다(§3).

**자율 루프가 아니다.** LLM 이 하는 일은 사건당 한 번의 질의-응답이고, 도구 호출은 Nexus 내부의 검색뿐이다. 목표를 향해 도구를 고르며 반복하는 루프는 v1 에 없다. 넣으려면 조회 횟수와 비용에 상한이 먼저 필요하다 — 그때 이 문서를 고친다.

## 2. 지키는 원칙

**판정은 결정적이고 설명은 비결정적이다.** 이 문장이 나머지 전부를 낳는다.

- 설명 생성이 실패하거나 느려도 **사건 처리가 막히지 않는다.** 번들은 이미 운영자 화면에 있고 설명은 뒤늦게 붙는다
- 설명이 틀려도 **판정이 바뀌지 않는다.** 최악의 경우 부정확한 문장 하나이고, 그것도 인용 검증이 걸러낸다
- 근거가 없으면 **모른다고 답한다.** 지어낸 설명은 없는 설명보다 나쁘다

**LLM 비인지를 picasso 쪽에서 지킨다.** picasso 가 기종을 모르는 것과 같은 이유로 LLM 을 몰라야 한다. 그래서 picasso 는 이 저장소를 호출하지 않는다(§3).

---

## 3. 트리거 — 호출 방향

**picasso 가 narrator 를 부르지 않는다.** 부르면 자기 소비자에 의존하게 되고, narrator 가 죽을 때 사건 처리가 멈춘다. 그것이 §2 의 첫 원칙을 깨는 가장 흔한 방식이다.

배선은 이렇다.

1. picasso 가 번들을 **레지스트리에 적재**한다 — 권위 있는 기록
2. 알림이 필요하면 **발행**한다 — picasso 는 누가 듣는지 모른다
3. narrator 가 **구독**하고, 전문은 적재분에서 읽는다
4. 발행을 놓치면 **적재분을 스캔해 따라잡는다**

발행은 알림이고 적재가 권위다. 구독자가 놓쳐도 복구된다.

**v1 은 발행 없이 적재 + 주기 스캔만으로 시작한다.** picasso 쪽 변경이 그만큼 작아지고, 지연이 초 단위로 늘어나는 것은 설명 층에서 문제가 되지 않는다.

트리거는 세 갈래다 — 사건 발생 시(설명 하나), 운영자 질의 시(대화형), 교대 종료 시(패턴 요약).

### 3.1 시간축 — 아는 시점과 처리되는 시점은 다르다

```
t0          로봇이 실패를 보고하거나 설비 신호가 오지 않음
t0+δ        picasso 판정 — 단위를 미완료로 닫고 번들 생성
t0+δ        번들 적재. 운영자 화면에 사건이 나타나고, 차단 알림도 이 시점
t0+δ+ε      수신기 인지 — 구독이면 수백 ms, 스캔이면 다음 주기
+수초        질의 구성 → 설명 생성 → 인용 검증
+           기록기가 사건에 설명을 붙인다. 화면의 「설명」 칸이 채워진다
```

**운영자는 `t0+δ` 에 이미 안다.** 번들을 만든 것이 picasso 이기 때문이다. 설명은 그 화면에 **나중에 채워지는 칸**이며, 승인도 설명을 기다리지 않는다. 그래서 이 층이 늦게 알아도, 아예 오지 않아도 사건 처리는 진행된다 — 설명만 비어 있다.

이것이 §2 첫 원칙의 실제 모습이다. 이 순서가 뒤집혀 설명을 기다려야 화면이 채워지면, 그 순간 LLM 이 운영 경로에 들어간 것이다.

### 3.2 멱등과 실패 기록

- **번들 id 기준으로 멱등하다.** 수신기가 같은 번들을 두 번 집어도 설명은 사건당 한 건이다
- **설명이 없는 이유를 구별해 기록한다.** 「아직 오지 않음」·「생성 실패(재시도 상한 초과)」·「근거 없음」 셋은 다른 상태다. 조용히 빈 칸으로 두면 운영자가 셋을 구별하지 못하고, 특히 **「근거 없음」 은 실패가 아니라 정상 출력이다**(§2)

## 4. 데이터와 권한

받거나 조회한다. 수집하지 않는다.

| 갈래 | 내용 |
|---|---|
| 사건 번들 | 분류, 깨진 사전 조건, 잔여 파지, 근거 창, 미결 여부, 효과-관측 어긋남, 대안 탐색 결과, 프로파일 개정판·계약 버전 |
| 코퍼스 | picasso 문서·ADR·한계 대장·검증 문서, 벤더 표면 조사 노트, 합성 SOP(합성 표시 필수) |
| 사건 이력 | 과거 번들과 그때의 승인·사후 검토 결과 |
| (선택) 텔레메트리 | OTel |

**읽기 전용을 권한으로 강제한다.** 로봇 제어 경로, 설비 쓰기, 명령 서비스 호출은 자격증명 수준에서 분리한다 — 규율로만 두면 어느 날 누가 "여기서 바로 보내면 편한데"를 한다.

**벤더 독점 문서는 코퍼스에 넣지 않는다.** picasso 가 벤더 SDK 를 저장소에 두지 않고 심볼명과 해시만 두는 규율을 지켜왔다. 여기서 매뉴얼을 적재하면 그 규율이 깨진다.

**사람 식별자는 설명에 싣지 않는다.** 승인자와 진단자는 사건에 붙지만, 원인 설명에 이름이 들어갈 이유가 없다.

## 5. 다룰 수 있는 층

| 다룰 수 있다 | 다룰 수 없다 |
|---|---|
| 계약 층의 실패 — 사전 조건 위반, 거절 코드, 멱등 충돌 | 로봇 내부 — 관절 제어, 모션 플래닝, 인식 실패의 물리적 원인 |
| 판정 층 — 완료 판정, 효과-관측 어긋남, 미결, 근거 등급 부족 | 설비·PLC 내부 — 센서 값과 래더 논리 |
| 어댑터 경계에서 관측된 것 — 벤더 거절 분류, 관측 불가 | 전역 라우팅·배차 (picasso 스코프 밖) |
| | 네트워크·인프라 — 브로커 장애, 전송 단절 |
| | 안전 계통의 판단 |

**"이 층에서는 여기까지 보이고 그 아래는 다른 자료가 필요하다"는 정답이다.** 회피가 아니라 에스컬레이션 대상을 지목하는 답이다. 층을 넘어 추측하기 시작하면 그것이 이 경계가 막으려던 실패다.

## 6. 자동 승인 — 자격은 선언으로만 생긴다

### 6.1 회복은 누가 실행하는가

narrator 는 로봇이나 어댑터에 명령하지 않는다. **미들웨어의 승인 API 를 부른다** — 사람이 누르던 그 버튼이다.

직접 명령을 금지하는 이유는 안전 취향이 아니라 **권위** 문제다. 명령 원천이 둘이 되면 미들웨어의 상태 기계가 모르는 명령이 흐르고, 멱등 보장(`task_id`·`revision`), 계획 시점 사슬 검사, 근거 등급 결합, 완료 판정이 전부 우회된다. 그 순간 미들웨어는 시스템의 권위가 아니라 참가자 하나로 떨어지고, 사후에 "무엇이 이 명령을 보냈나"를 추적할 수 없다.

승인 API 를 부르면 실행은 여전히 미들웨어가 하고, 이 층의 권한은 **승인 한 번**에 그친다. 조치 내용은 탐색기가 만든 것이며 이 층이 짜지 않는다.

| 권한 | 범위 |
|---|---|
| **읽기** — 설명 생성, 근거 인용 | 항상 |
| **자동 승인** — 탐색기가 낸 조치를 사람 대신 승인 | §6.2 의 선언 목록에 있을 때만. 감사 필수 |
| **직접 명령** | 없음 |

감사에 **승인자가 사람인지 이 층인지** 남긴다. 없으면 사후에 구별되지 않는다. 이 층이 승인한 건도 사후 검토 대상이며, 이의율은 사람 승인과 **따로** 집계한다.

### 6.2 자격은 선언으로만 생기고, 런타임은 좁히기만 한다

**계산된 자격은 계산이 틀리면 조용히 넓어진다.** 조건 하나를 잘못 평가하면 승인 자격이 생기고 아무도 그 순간을 보지 못한다. **선언된 자격은 사람의 행위이므로 감사 가능하고 만료를 걸 수 있다.** 프로파일의 사전 조건을 벤더 1차 자료 없이 선언하지 않는 규율, `UNKNOWN` 은 선언하지 않는 것이라는 규율과 같은 원칙이다.

- 사람이 "이 조치는 자동 승인 가능"이라고 **선언**한다 — 조치 유형 단위, 범위(셀·기종·스킬)를 붙여서
- 선언에는 **근거**가 붙는다 — 누가, 무엇을 근거로, 언제, 어느 프로파일 개정판과 계약 버전에 대해
- 런타임은 **선언 목록에 있는가**만 본다. 계산으로 자격을 부여하지 않는다
- 런타임 조건은 **좁히는 방향으로만** 작동한다 — 반복 카운터 초과, 범위 불일치, 관측 불가면 자격이 사라진다

**선언은 만료된다.** 프로파일 개정판 변경, 계약 마이너 변경, 벤더 펌웨어 변경, 또는 기간. 만료되면 자동 자격이 사라지고 다시 사람에게 올라간다.

**선언이 있을 자리는 프로파일이 아니다.** 프로파일은 기종의 사실이고 자동 승인 허용은 **현장 정책**이다 — 같은 기종이라도 셀마다 다를 수 있다. `registry` 가 바인딩·변경 계획·사이트 카탈로그를 다루므로 그쪽이 자리다.

### 6.3 선언의 심사 기준 — 런타임 게이트가 아니다

아래 넷은 **선언을 승인할 때 사람이 확인하는 기준**이다. 런타임에 이것을 계산해 자격을 주지 않는다.

1. **가역성** — 실패해도 물리적으로 되돌릴 수 있는가
2. **관측 가능성** — 조치의 결과를 이 층이 관측할 수 있는가. 못 하면 미결을 하나 더 만드는 것이다
3. **영향 범위** — 이 단위와 이 기체 안에서 끝나는가
4. **결정성** — 조치가 선언된 효과로 완전히 기술되는가. **조치 선택에 LLM 판단이 개입하면 자격 없음**

### 6.4 조치의 계보 — 네 칸 사다리

탐색기가 계산한 조치는 **선언된 효과 위에서만** 맞다. 효과 선언이 벤더 실제와 다르면 조치는 의도와 다르게 동작한다. 실행 이력이 있는 조치는 그 가정을 한 번 이상 검증한 것이고, 신규 조치는 아직 아니다. 그래서 칸을 건너뛰지 않는다.

| 단계 | 상태 | 올라가는 조건 |
|---|---|---|
| **계산됨** | 탐색기가 낸 제안. 아무도 실행한 적 없음 | — |
| **시뮬 검증됨** | 미믹에서 그 실패를 재현하고 조치를 실행해 해소됨 | 재생 시험 통과 |
| **현장 검증됨** | 실환경에서 사람이 승인해 N 회 통과, 사후 검토 이의 없음 | 관리자가 승격 경로에 올린 뒤 N 회 무사 |
| **자동 승인** | 선언 목록에 등재 | 관리자의 선언 + 근거 + 만료 |

**관리자 승인의 의미는 "자동화"가 아니라 "승격 경로에 올림"이다.** 신규 제안을 승인하면 두 번째나 세 번째 칸에 들어간다. 그 뒤 몇 번은 여전히 사람이 누르지만 시스템이 그 조치를 우선 제안하고 결과를 기록한다. N 회 무사통과하면 올라가고, **한 번이라도 실패하거나 이의가 붙으면 강등되며 사유가 남는다.**

이 사다리는 Yggdrasil 의 활성화 사다리와 같은 모양이다 — 승인과 서명과 원장으로 단계를 올리는 구조.

### 6.5 검토 화면이 묻는 질문

신규 조치를 사람이 볼 때 확인할 것은 "이 조치가 목표를 달성하나"가 **아니다.** 그것은 탐색기가 이미 계산했다.

**"선언에 없는 부작용이 있나"** 가 사람이 답할 질문이다. 놓기가 목표 상태로는 맞아도 물리적으로 부품을 떨어뜨려 손상시킬 수 있다는 것은 효과 선언에 없다. 검토 화면이 이 질문을 묻지 않으면 검토는 의례가 된다.

### 6.6 반복 승인의 두 출구

같은 조치의 반복 승인은 결함 신호이기도 하고 자동화 후보의 근거이기도 하다. 모순이 아니라 둘이 다른 것이다.

| 반복되는 것 | 성격 | 출구 |
|---|---|---|
| 증상을 우회하는 조치 | 근본 원인 미해결 | **근본 원인 항목으로 올린다** |
| 설계된 정상 복구 경로 | 원래 그렇게 하면 되는데 사람 손을 거친다 | **자동 승인 선언 후보로 올린다** |

**어느 쪽인지는 시스템이 판정할 수 없다.** 근본 원인을 고치는지 증상을 덮는지는 도메인 판단이고, 시스템이 정하게 하면 우회가 자동화된다. 시스템은 후보를 제시하고 **사람이 어느 출구로 보낼지 선언한다.**

### 6.7 신규 제안은 그 자체로 산출물이다

아무도 시도하지 않은 복구 경로를 시스템이 찾아내는 것은 운영 지식의 확장이다. 그리고 사람이 그것을 검토하는 과정에서 **사람의 이해가 늘어난다.** 조용히 자동화하면 줄어든다. 신규 제안을 반드시 사람을 거치게 하는 것은 안전 때문만이 아니라 §7 의 표상 유지 관점에서도 맞다 — 이 설계에서 두 목적이 같은 방향을 가리키는 드문 지점이다.

### 6.8 v1 의 상태

**경로와 자격 검사와 감사를 만들고, 켜는 것은 설정으로 두며 기본값은 끔이다.**

현재 상태 축(파지 하나)에서 §6.3 의 넷을 다 만족하는 조치는 놓기 정도뿐이다. 데모에서는 자격을 만족하는 조치 하나로 자동 승인이 실제로 도는 것과, 나머지가 자격 미달로 사람에게 올라가는 것을 함께 보인다.

기준 없이 하나씩 자동화하면 그 목록이 곧 아무도 왜 그런지 모르는 예외 집합이 된다.

## 7. 알림

| 차단 — 사람이 답해야 진행 | 통지 — 알고만 있으면 됨 |
|---|---|
| 운영자 판단 상태 | 자동 회복된 일시 실패 (개별이 아니라 건수) |
| 승인이 필요한 대안 | 다른 기체로 진행 중인 사건 |
| 대안 없음 + 라인 정지 중 | 교대 요약 |
| 안전 정지 후 복구 | |
| 의도적 비자동화로 가려둔 사건 | |

둘을 섞으면 알림 피로가 오고 둘 다 무시된다.

**패턴에 걸리는 에스컬레이션**은 따로다.

- 같은 대안의 반복 승인 → 근본 원인 미해결
- 이의율 상승 → 원인 지목이 현실과 어긋나기 시작
- 근거 없음 비율 상승 → 코퍼스가 낡았다
- 모델 밖 사건율 상승 → 능력 모델 갱신 소환
- **이의율이 0 으로 수렴 → 아무도 안 읽는다**

마지막이 역설적이지만 제일 중요하다. 지표가 좋아 보이는 방향으로 움직이는데 감시가 죽은 상태다.

## 8. 한계 — 지금 없는 것

- **상태 축이 파지 하나(4값)** — 위치·슬롯 점유·자재 유무가 축에 없어 대안 탐색이 구조적으로 얕다. 설명 층이 두꺼워져도 탐색이 깊어지지 않는다
- **사후 대조가 없다** — 원인 지목이 실제로 맞았는지는 정비 실적과 재발 여부로만 확정되고 그 경로가 없다(picasso §15.147)
- **이해 밀도 계량이 없다** — 사람이 시스템 없이 진단을 설명할 수 있는 비율은 시스템 밖의 사실이다(picasso §15.151)
- **코퍼스의 SOP 가 합성이다** — 실제 현장 문서가 아니다
- **평가 규모가 데모다** — 시나리오 여섯 종
