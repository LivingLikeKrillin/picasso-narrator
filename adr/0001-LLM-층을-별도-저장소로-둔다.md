# ADR 1 — LLM 층을 별도 저장소로 둔다

- **상태** 받아들임 (2026-09-17). 실물로 검증됨 (2026-09-18·19)
- **범위** 이 저장소(`picasso-narrator`)와 `picasso` 의 관계
- **참조** `BOUNDARY.md` §1·§3 · `picasso ADR 9`(소비자 존재 원칙) · `picasso ADR 40`(질의이고 계약이 아니다)

> 번호는 **이 저장소의 것**이다. 본문에서 `picasso ADR 9` 처럼 저장소 이름이 붙은
> 것은 남의 결정이고, 그쪽 번호 체계를 잇지 않는다.

## 맥락

`picasso` 는 이기종 로봇 미들웨어이고 **결정적이어야 한다.** 같은 입력에 같은 판정이
나와야 하고, 그 판정이 왜 그렇게 났는지 코드로 따라갈 수 있어야 한다. 조치 선택에
LLM 판단이 개입하면 그 순간 자격이 없다(`BOUNDARY.md` §5).

그런데 실패한 사건을 운영자가 읽을 때 **번들만으로 원인이 하나로 안 좁혀지는 자리**가
있다. 거기서 후보를 정렬하고 근거를 인용해 주는 일은 값이 있다. 그 일은 LLM 이 잘한다.

**두 요구가 한 저장소 안에서 부딪힌다.** 「결정적이어야 한다」와 「LLM 이 필요하다」.

## 결정

**설명 층을 별도 저장소에 둔다.** `picasso` 는 이 저장소의 존재를 모른다.

- `picasso` 의 LLM 의존은 **0 이다.** 라이브러리도, 설정 항목도, 환경 변수도 없다
- 이 저장소의 어떤 코드도 `picasso` 를 수정하지 않는다
- 넘어오는 것은 **파일 한 벌**이다 — `incidents.jsonl` · `remedy-searches.jsonl` ·
  `manifest.json`. `manifest.json` 이 마지막에 나타나는 것이 「한 벌이 다 나왔다」는 신호다
- 이 저장소 안에서도 LLM 이 닿는 곳은 **`explainer/` 하나다.** 나머지 셋
  (`receiver`·`composer`·`recorder`)은 LLM 이 없다

## 왜 이 방식인가 — 경계를 **코드 배치로 증명한다**

같은 저장소에 두고 「LLM 은 여기까지만」이라고 **문서로 적는** 방법도 있다. 그러면
증명이 **약속**이 된다. 약속은 지켜지는지 밖에서 확인할 수 없고, 급할 때 먼저 깨진다.

저장소를 가르면 확인이 **기계적**이 된다.

| 묻는 것 | 어떻게 답하나 |
|---|---|
| picasso 가 LLM 을 쓰나 | 의존성 목록을 본다. 없으면 없다 |
| 설명이 판정에 영향을 주나 | 설명 층이 picasso 를 import 하지 않는다. 파일만 읽는다 |
| LLM 이 자율로 도나 | `explainer/` 가 사건당 한 번 묻는다. `tests/test_explainer_once.py` 가 고정한다 |

**이것이 이 프로젝트의 논지이고, 저장소가 셋인 이유다.**

## 실물이 이 결정을 시험한 두 번

**(가) 경계가 실제로 밀렸다.** 2026-09-18, `picasso` 쪽이 인계 설명 파일을 **이 저장소
안에** 써 넣었다. 편했기 때문이다. 알렸더니 그쪽이 자기 저장소에 `handoff/narrator/`
를 만들고, 산출을 고정하는 시험(`HandoffFixtureTest`)과 `CLAUDE.md` 조항을 넣었다.

**문서로만 적어 뒀으면 이 일은 안 걸렸을 것이다.** 남의 저장소에 파일이 생기는 것은
눈에 띄지만, 같은 저장소 안에서 import 한 줄이 느는 것은 안 띈다.

**(나) 상류가 죽어도 아래층이 안 죽는다.** 2026-09-19, Khala 의 합성 브리지가 실행
중에 사라져 뒤에 줄 선 호출이 전부 실패했다(`TO-KHALA-2026-09-19-브리지-벽.md`).
그동안 `picasso` 의 어떤 경로도 그 브리지를 부르지 않는다 — **부를 코드가 없다.**
설명이 안 나오는 것과 로봇 판정이 멈추는 것이 **다른 사건이 된다.**

이것이 이 결정이 사는 이유다. 한 저장소였으면 「설명이 느리다」를 고치려다 판정
경로의 타임아웃을 만졌을 것이다.

## 치르는 값

솔직히 적는다. 싸지 않다.

- **인계가 규약이 된다.** 함수 호출이면 공짜일 것이 파일 규약·스키마 버전·멱등
  열쇠가 된다. `(runId, digest)` 를 열쇠로 쓰는 이유도 여기서 나왔다(`BOUNDARY.md` §3.4)
- **한 바퀴가 느려진다.** 번들에 칸이 하나 늘면 저쪽이 내고 이쪽이 받는 두 판이 필요하다.
  실제로 21칸 → 30칸을 받는 데 요청 한 번과 왕복 하루가 들었다
- **두 저장소를 같이 봐야 하는 사람이 생긴다.** 그 비용은 문서로 갚는다 —
  `BOUNDARY.md` 가 코드보다 먼저 쓰인 이유다

이 값을 치르는 것이 맞다고 본 이유는 하나다. **결정성은 잃으면 되돌릴 수 없다.**
한 번 LLM 판단이 판정 경로에 섞이면, 그 뒤의 모든 판정에 대해 「이건 결정적인가」를
다시 물어야 한다. 인계 규약은 비싸지만 **되돌릴 수 있다.**

## 안 고른 길

| 대안 | 왜 안 했나 |
|---|---|
| 한 저장소, 모듈 경계 | 증명이 약속이 된다. 위 (가)가 그 약속이 어떻게 밀리는지 보여준다 |
| picasso 가 설명을 **호출** | 호출하는 순간 picasso 가 소비자의 존재를 안다. `picasso ADR 9` 가 막는 자리다 |
| 설명을 picasso 의 플러그인으로 | 같은 프로세스에 LLM 의존이 들어온다. 의존성 목록이 더는 답이 안 된다 |
| 설명 층이 picasso DB 를 직접 읽기 | 읽는 순간 저쪽 스키마 변경이 이쪽을 깬다. 파일 규약은 버전이 붙는다 |

## 이 결정이 틀렸다는 신호

**적어 두지 않으면 틀려도 안 바꾸게 된다.**

- **인계 규약을 고치는 일이 기능 추가보다 잦아진다.** 그러면 경계가 잘못된 자리에 있다
- **설명 층이 번들에 없는 값을 자꾸 필요로 한다.** 번들이 계속 커지면 경계가 아니라
  이음매가 잘못 그어진 것이다. 30칸까지는 늘릴 만했다. 이 방향이 계속되는지 본다
- **picasso 의 의존성 목록에 LLM 관련이 하나라도 들어온다.** 그 순간 이 ADR 은 죽는다.
  논지가 아니라 장식이 된다
