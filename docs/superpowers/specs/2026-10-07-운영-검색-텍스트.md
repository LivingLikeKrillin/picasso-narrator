# 운영 검색 텍스트 — 운영 경로가 `search_text` 에 Q3 을 싣는다

- 작성 2026-10-07 · 버전 2 · 상태: **설계 — 독립 검토 반영**
- 기반: 검색 텍스트 칸 측정(설계서 `docs/superpowers/specs/2026-10-06-검색-텍스트-칸.md`, 결과 `eval/RESULTS.md` 「검색 텍스트 칸 — 두 경로
  (2026-10-07)」). 두 경로 다 승격됐다 — 설명 경로 절차 문서 인용 G0 7/10 → GS 10/10, 진단 경로 D0 16/20 → DS 18/20, 가드레일 지표 다
  충족. 실행 전에 박은 규칙으로 운영 질의 변경을 사전 등록할 후보가 됐고, 사용자가 「진행」으로 정했다(2026-10-07)
- **이 문서는 운영 경로를 바꾸는 설계다.** 앞 측정들과 달리 측정용 실행기가 아니라 운영 코드가 보내는 요청이 바뀐다
- **버전 2 에서 바뀐 것(독립 검토, Opus — MUST 다섯, SHOULD 여섯).**
  - **MUST 1 — 설명 경로의 같음 범위.** 골든셋 G1 · G10 · G11 은 골든셋에만 있는 탐색 쌍(`compose(bundle, search)`)으로 지은 질의라
    운영(`receiver/pipeline.py` 는 쌍을 짓지 않음)이 그 본문을 만들지 않는다. 그래서 같음은 설명 경로 아홉(G2~G9 · S1)의 운영 본문 같음과,
    쌍이 있는 셋의 Q3 짓기 함수 수준 같음으로 나눈다. 그리고 효과의 몫을 다시 센다 — GS 가 올린 셋(G1 · G6 · G11) 가운데 G1 · G11 은
    운영이 보내지 않는 본문이고, 운영과 같은 본문인 절차 사건 일곱(G2 · G3 · G4 · G6 · G7 · G8 · G9)만 세면 G0 6/7 → GS 7/7 이다. 승격
    판정은 실행 전 규칙대로라 그대로다
  - **MUST 2 — 진단 경로의 같음.** 권고 측정기 경로(`run_diagnosis` + `eval/recommend.py` 의 `client_for`, 빼는 종류 `spec` · `design_doc` ·
    `case`)의 본문이 DS 와 21/21 같다(검토 탐침). 운영 워커(`diagnose/worker.py`)는 빼는 종류가 `INCIDENT_EXCLUDED`(`spec` · `design_doc`)라
    그 본문에서 `exclude_doc_types` 의 `case` 하나만 다르다. 과거 사례는 테넌트 `narrator` 에 있어 지금 `case` 는 picasso 테넌트에서
    아무것도 거르지 않는다(진단 계약 초안이 「요청 인자 하나가 다른 것」이라고 이미 적음). 워커의 클라이언트는 `main()` 안의 닫힘이라
    모듈 수준 함수(예: `make_client`)로 꺼내 시험과 실제 확인이 같은 함수를 쓰게 한다
  - **MUST 3 — 측정기.** 골든셋 측정기(`eval/run.py` · `eval/measure.py`)는 운영 수신기(`explain`)를 거치지 않고 Q0 글을 바로
    `ask_and_record` 에 넘긴다. 이번 변경에서는 측정기(골든셋 측정기와 권고 측정기 `eval/recommend.py`)를 바꾸지 않는다 — 기준선을 바뀐
    운영으로 옮기는 것은 다음 측정의 설계서가 정한다
  - **MUST 4 — 배선.** `search_text` 를 보낼지를 앞 실행기가 지나가는 자리에서 정하면 그 실행기들의 본문이 바뀐다(검토가 흉내 내 보니
    D0 에 키가 생기고 실행기 시험 여섯이 실패). 그래서 켜는 자리는 운영 진입점 둘(수신기 파이프라인 · 진단 워커의 `main`)뿐이고 나머지는
    기본값이 꺼짐이다
  - **MUST 5 — 실제 서비스 확인.** 지정을 고쳤다(§3)
  - **SHOULD 여섯.** Q3 정의를 측정 함수와 같은 것으로 못 박고 갈래 넷을 시험한다(S1). 바뀐 기록을 가를 표지를 뒀다(S2). 끝난 측정을
    다시 세는 명령을 적었다(S3). 같음 검사가 해시만 있는 기록 대신 측정 코드로 다시 지은 본문과도 견준다(S4). 진단 계약 §3.5 와 README ·
    그림을 갱신한다(S5). 되돌림의 빈틈(워커 재기동, 첫 결과 저장소, 버전 필드 기대 값)을 적었다(S6)

## 0. 무엇을 바꾸나

- **운영 경로 둘이 khala `/search/answer` 에 보내는 본문에 `search_text` = Q3 을 더한다.** 설명 경로는 수신기(`receiver/pipeline.py` 의
  `run_batch` 가 사건 · 조치 탐색 기록마다 `_one` → `ask_and_record`), 진단 경로는 워커(`diagnose/worker.py` 의 `main` → `diagnose` →
  `run_diagnosis`). `query` 는 지금 그대로 Q0(`composer.query.Query.text`)이고 `answer_context` 도 그대로다
- **Q3 의 정의.** 검색 텍스트 칸 측정 때(`a6c55c6`) `eval/ask_trial.py` 의 `texts(query)["Q3"]` 와 바이트까지 같은 함수다. 그 함수는 고정
  질문(`ASK`)을 빼고, 식별자 토큰(12개까지, khala `identifiers.py` 정규식의 사본)을 Q0 의 차례로 앞에 두고(스칼라 사실만으로 토큰 차례가
  Q0 와 같으면 앞에 세우지 않음), 스칼라 사실만 싣는다(dict · list 사실은 빠진다). 운영 코드에서는 `composer/query.py` 의 `Query` 가
  짓는다(예: 속성 `search_text`). 측정 코드를 운영 코드가 가져다 쓰지 않는다(의존 방향). 운영에서는 Q3 이 비면 예외를 내지 않고 키를 안
  보낸다(khala 도 빈 값을 안 준 것으로 받는다)
- **배선(가장 덜 건드리는 길, 검토 권고).** `nexus_client` 가 돌려주는 `search` 에 선택 인자 `search_text=None`(비거나 None 이면 키를 안
  보냄), `ask_once` · `ask_and_record` 는 `search_text=None` 을 넘겨받기만 하고 None 이면 지금처럼 `search(text)` 를 인자 하나로 부른다.
  설명 경로는 `_one` 이 `query.search_text` 를 넘기고, 진단 경로는 `run_diagnosis` · `diagnose` 에 켜는 인자(기본 꺼짐)를 두고 워커
  `main` 만 켠다. 앞 실행기와 측정기는 기본값으로 부르므로 본문이 바이트까지 그대로다
- **운영자 질의를 보내는 자리는 운영 코드에 없다**(측정기와 실행기에만 있다). 그래서 운영자 질의는 이 변경과 무관하다
- **진단 계약(초안 0.6)의 요청 · 응답 칸과 koshei 에 돌려주는 응답 모양은 바뀌지 않는다.** 다만 계약 §3.5 가 khala 에 보내는 모양(`query`
  = compose 글, `answer_context`)을 적고 있으므로 거기에 `search_text` = Q3 을 더해 적는다(이 계층 안의 문서 갱신이고 koshei 쪽 칸은 안
  바뀐다)
- **바꾸지 않는 것** — 프롬프트(khala 쪽), 답변 컨텍스트, 빼는 종류, `top_k`, 식별자 채널, 시도 규칙, 판정(`diagnose/judge.py`), 기록 행의
  형식, 측정기와 앞 실행기

## 1. 같음 — 이 변경이 기대는 사실

- **측정의 GS · DS 요청은 운영 클라이언트 `nexus_client` 가 지은 본문에 `search_text` 하나만 더한 것이었다.** 운영이 같은 본문을 보내면
  측정 결과가 운영에 선다. 다만 결과가 넘어오려면 khala 쪽 상태(모델 · 프롬프트 · 코퍼스 · 검색 설정)도 측정 때와 같아야 한다 — 측정 때
  프롬프트 `efe1e242c0e3` · 코퍼스 `a9dfe99ac26c` · 검색 설정 `b071397c854c`
- **같음 검사(실제 서비스 없이, 시험으로)**
  - 설명 경로 아홉(G2 · G3 · G4 · G5 · G6 · G7 · G8 · G9 · S1): 운영 수신기(`explain` 경로)가 그 번들로 짓는 본문이 측정 기록
    `eval/st/g-1.json` 의 GS 줄 본문 해시(측정의 직렬화 `json.dumps(body, ensure_ascii=False, sort_keys=True, separators=(",", ":"))` 의
    sha256)와 같다. 재발 횟수는 측정과 같이 픽스처 이력으로 센다(검토 탐침: G4~G9 는 이력으로 세든 번들만으로 세든 0/0 으로 같고 G2 · G3
    는 이력으로 세야 같다)
  - 설명 경로 셋(G1 · G10 · G11, 탐색 쌍이 있는 것): 운영 `Query.search_text` 가 측정 기록의 GS `search_text` 해시와 같다(Q3 짓기 함수
    수준). 본문 전체는 운영이 짓지 않으므로 견주지 않는다
  - 진단 경로 스물하나: `run_diagnosis` 를 켬으로 권고 측정기 클라이언트(`eval/recommend.py` 의 `client_for`)로 부른 본문이
    `eval/st/d-1.json` 의 DS 줄 본문 해시와 같다. 그리고 워커의 클라이언트(`make_client`)로 부른 본문은 그 본문과 `exclude_doc_types` 에서
    `case` 하나만 다르다
  - 운영자 질의 셋은 `search_text` 키가 없다(측정기 쪽 사실, 운영 코드에는 자리가 없음)
  - 기록에는 해시만 있으므로(설명 경로 줄은 해시와 길이뿐, 진단 경로 줄은 질의 · 답변 컨텍스트 글은 있으나 `search_text` 글은 없음) 시험은
    측정 코드(`eval/query_trial.py` 의 `queries` · `eval/ask_trial.py` 의 `texts`)로 다시 지은 본문과도 견주어, 어긋날 때 어느 칸이 다른지
    보이게 한다(검토 탐침: 지금 측정 코드가 GS 열다섯 · DS 스물하나의 본문 해시를 다 재현한다)
- **Q3 짓기의 갈래 넷을 합성 `Query` 로 시험한다** — 식별자 토큰 12개 초과, 조회 지시가 붙는 경우, 토큰을 앞에 안 세우는 갈래(q2 = q1),
  빈 Q3(키를 안 보냄)
- **효과의 몫(서술)** — 설명 경로의 +3 가운데 운영으로 넘어오는 것은 G6 하나다(운영과 같은 본문인 절차 사건 일곱에서 G0 6/7 → GS 7/7).
  진단 경로는 권고 측정기 본문과 21/21 같아 +2(R01 · R07)가 운영 워커 본문(`case` 한 칸 다름)에 넘어오는 것으로 읽는다

## 2. 앞 실행기 · 측정기 · 끝난 측정

- **앞 실험 실행기(`eval/fusion_trial.py` · `eval/query_trial.py` · `eval/ask_trial.py` · `eval/gen_trial.py` · `eval/gen_diag_trial.py` ·
  `eval/st_trial.py`)와 측정기(`eval/run.py` · `eval/measure.py` · `eval/recommend.py`)는 고치지 않는다.** 그들의 시험이 바뀌지 않고
  통과하는 것이 「보내는 본문이 그대로」의 증명이다
- 운영 시험 가운데 가짜 `search`(인자 하나짜리)를 쓰는 것(예: 수신기 파이프라인 시험)은 키워드 인자를 받게 고친다 — 운영 시험이라 고쳐도
  되고 그 시험의 수는 안 바뀐다
- **끝난 측정의 집계.** `eval/st_trial.py` 의 평가 도구는 실행기 · 평가 도구 코드를 집계 때의 HEAD 와 견주므로, 운영 코드가 바뀐 HEAD 에서
  `python -m eval.st_trial tally` 를 돌리면 「평가 도구 코드가 집계 때의 HEAD 와 다르다」로 성립 안 함 · 판정 「운영 질의 그대로」가 찍혀
  승격이 뒤집힌 것처럼 보인다. 끝난 측정은 기록 커밋에서 다시 센다 — `git worktree add <임시 폴더> a6c55c6` 뒤 그 폴더에서
  `python -m eval.st_trial tally`. 이 명령을 `eval/RESULTS.md` 의 그 절과 `STATE.md` 에 적는다. 다른 실행기들의 집계는 코드를 HEAD 와
  견주지 않고 본문도 그대로라 영향이 없다

## 3. 확인 — 실행 전에 박는다

- **오프라인(필수, 커밋 전)** — §1 의 같음 검사가 다 같고, 앞 실행기 · 측정기의 시험이 바뀌지 않고 통과하고, 전체 시험이 통과한다(기준 수는
  새 시험만큼 는다)
- **실제 서비스(한 번, 짧게, 배선 확인이지 측정이 아니다 — 지표를 세지 않는다)**
  - 설명 경로: 골든셋 G4~G9 가운데 하나(정지 코드 문서 사건이 아닌 것으로 계획서가 정한다)의 사건 한 줄만 든 한 벌로 운영 수신기
    (`explain`)를 부른다. `python -m receiver` 는 한 벌을 통째로 부르므로(run-1 은 13건) 한 줄짜리 한 벌을 스크래치에 짓거나 한 줄짜리
    묶음으로 `explain` 을 부르는 확인 스크립트를 쓴다. `--out` 은 새 빈 폴더, 승인 시도(`--approve`)는 켜지 않는다
  - 진단 경로: R01 을 워커의 클라이언트(`make_client`)로 `run_diagnosis`(켬)에 직접 부른다. 워커 프로세스가 떠 있으면 내리고 한다(동시
    한도가 한 프로세스 안의 것)
  - 되울린 `search_text_len` 은 기록 행에 안 남으므로(`recorder/record.py` 의 계측 칸에 없음) 확인 스크립트가 전송을 감싸 보낸 본문과
    응답을 직접 잡는다
  - 보는 것: 성공 봉투, 보낸 본문의 해시가 §1 에서 기대한 해시와 같음(설명 경로는 측정의 GS 줄 해시, 진단 경로는 측정 DS 해시에서 `case`
    한 칸 다른 본문), 되울린 `search_text_len` 이 보낸 길이와 같음, 생성 실패 없음, 버전 필드
  - 버전 필드의 기준: 프롬프트 `efe1e242c0e3` · 검색 설정 `b071397c854c` 와 같아야 「측정 결과가 운영에 넘어온다」를 말한다. 다르면
    배선은 맞아도 그 말을 하지 않고 적는다. 코퍼스는 그 사이 바뀌었을 수 있고(측정 뒤 `58cda9065b40`) 적기만 한다
  - 확인 전에 khala 에 알린다(동결은 청하지 않는다). 십 분 안팎이다
- **되돌림** — 오프라인 같음 검사가 하나라도 다르면 커밋하지 않는다. 실제 서비스 확인에서 422(모르는 칸) · 되울림 불일치 · 생성 실패가
  나면 운영 변경 커밋을 되돌리고(`git revert`) 까닭을 적는다. 워커는 띄울 때 커밋을 정하므로 커밋 뒤와 되돌린 뒤에 워커를 다시 띄운다.
  첫 결과 저장소는 멱등성 키로 결과를 캐시하므로 되돌린 뒤에도 같은 키에는 바뀐 운영으로 지은 답이 돌아간다(의도대로, 적어 둔다)

## 5. 측정에서 본 것 중 운영에 따라오는 것 (서술, 이 변경에서 고치지 않음)
