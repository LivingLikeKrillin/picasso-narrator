# 질의 줄이기의 실행기와 셈 — 실행 기록

> 설계서: `docs/superpowers/specs/2026-10-01-질의-줄이기.md`. 이 문서는 계획서 자리에 두는 **실행 기록**이다 — 융합 처치 판의 실행기를
> 가져다 쓰는 작은 측정 도구라 제어 세션이 직접 지었고, 독립 검토 하나(설계와 코드를 함께)를 받았다.

**Goal:** khala 가 소유자 결정으로 융합 처치를 멈추고 먼저 보기로 한 호출자 쪽 처치 — 검색이 받는 글에서 구조 사실을 빼면 절차 문서가
오는가 — 를 생성 없이 잰다.

**Architecture:** `eval/query_trial.py` 하나. 운영 경로와 같은 재료의 `Query` 에서 세 글(Q0 그대로 · Q1 구조 사실 뺌 · Q2 구조 사실 빼고
Q0 의 식별자 토큰을 차례까지 지킴)을 짓고, 융합 처치 판의 `call` · `row_of` · `validity` 와 부 변수 함수를 그대로 쓴다. 셈은 Q0 의 검색으로
실험군을 짝짓는 순수 함수다. 운영 코드(`composer/query.py` · `diagnose/core.py` · `eval/run.py`)와 `eval/fusion_trial.py` 는 고치지 않는다.

**Tech Stack:** Python 3, pytest.

## 한 것

- [x] **설계 전 셈(판 아님).** 항목마다 세 글의 길이와 식별자 토큰 — Q0 는 많아야 2,404자이고 2,000자 넘는 것이 열여섯, Q1 은 807자,
  Q2 는 866자까지다(판 2 의 정의로 다시 셈). Q0 의 식별자 토큰은 많아야 일곱이라 khala 의 상한 12 에 안 걸린다. Q1 이 잃는 토큰은 대개
  고장 객체의 잡음(`KEY_SKILL_ID` · `KIND_UNTIL_CLEARED`)이지만 벤더 정지 코드(`X_FIXTURE_GRIPPER_SLIP`) · 실패 종류
  (`SKILL_EXECUTION_FAILED`) · 조치 걸음의 `HOLD_KIND_*` 도 있다
- [x] **실행기 · 셈 · 시험(판 1).** `eval/query_trial.py`, `tests/test_eval_query_trial.py`(시험 일곱). 모듈을 치운 채 시험이 먼저
  빨갰고(수집 오류) 모듈과 함께 초록이었다
- [x] **실물 확인(판 아님, 기록 안 함).** R01 을 세 글로 한 번씩 불러, 응답이 쓴 식별자 토큰이 이 층이 보낸 글에서 뽑은 것과 세 실험군
  다 같고 성립 검사에 걸린 것이 없음을 봤다(검색 구간 10.8 → 3.7 · 5.0초). 절차 문서가 들었는지는 보지 않았다 — 판에서 본다
- [x] **독립 검토(Opus, 설계와 코드)** — 판정 「MUST 두 건을 고친 뒤 돈다」. 검토는 읽기만 했고 36 항목의 세 글 · 본문 · 검색 열쇠를 가짜
  전송으로 지어 셌다
  - **맞는 것** — Q0 본문이 융합 판 `t0-2` 와 36/36 같고, T0 응답의 `identifier_channel` 이 이 층의 토큰 추출과 36/36 같다(차례까지).
    질의를 뺀 본문은 세 실험군이 바이트까지 같다
  - **M1** — 판 1 의 Q2 는 토큰 집합만 지키고 차례를 32 검색 가운데 22 에서 바꿨다. khala 의 식별자 채널은 토큰을 이은 글로 벡터도 돌아
    차례가 순위를 바꾼다. 실물 확인이 못 잡은 것은 응답 토큰을 Q0 가 아니라 보낸 글과 견줬기 때문이다
  - **M2** — Q1 · Q2 가 서로 다른 Q0 검색을 합친다(Q1 스물 · Q2 스물둘). 부호 검정이 단위를 독립으로 봐 p 값이 실제보다 작게 나온다
  - **SHOULD** — 넘김 규칙에 정밀도 가드가 없고 실험군이 빠져도 넘김을 낸다(S1), 처치 검사가 셈에서 강제되지 않고 토큰 검사가 첫 판만
    본다(S2), 부 변수의 근거 분량 · Q0 대비 지연 · 고장의 분모가 없다(S3), 빠지는 열쇠의 목록(S4), Q1 대 Q2 가 없다(S5), 시험 여덟 자리(S6)
  - **NIT** — 토큰 상한(N1), 견주지 않았을 때의 「없음」(N2), G1 은 시간 초과가 아니었고 `q0-1` 은 다시 돌 확률이 높다(N4), R01 짝의
    상태(N5), 융합 판 T0 와 판끼리의 khala 신원(N6)
- [x] **판 2 로 고침.** 위를 다 받았다
  - **Q2** — Q0 의 토큰 전부를 Q0 의 차례로 물음 바로 뒤에 둔다. 서른여섯 항목 모두 차례까지 같다
  - **합쳐짐** — 실험군마다 서로 다른 검색과 합쳐짐의 목록을 내고 p 값을 안 낸다(무리 단위 검정 대신 — 실효 표본이 열여섯 · 열여덟이다)
  - **넘김 규칙** — 기대 있는 검색의 틀린 절차가 Q0 보다 늘면 안 넘기고, 세 실험군이 다 성립해야 정한다. 손실은 따로 막지 않고 적는다
  - **성립 조건** — khala 코드 신원(판 전부의 앞뒤가 한 벌), 결정론, 처치(모든 성립한 판의 토큰 · Q2 의 차례 · Q1 과 Q2 가 바꾼 항목),
    음성 대조가 깨지면 머리 수치가 아니다
  - **시험 열** — 셋을 더했다. 검토가 짚은 결함 열둘을 하나씩 실행기에 되돌려 넣어 열둘 다 시험이 빨개지는 것을 봤다(Q2 를 끝에 붙이기 ·
    조회 지시 잃기 · 틀린 절차 가드 빼기 · 빠진 실험군 봐주기 · 토큰 검사를 첫 판만 · Q2 토큰 검사 빼기 · 합쳐짐 안 세기 · F1 칸 보내기 ·
    판 안의 무리 검사 빼기 · 실험군 글의 무리 검사 빼기 · khala 신원 검사 빼기 · 「판정 안 함」 대신 「없음」)
- [x] **커밋 뒤 여섯 판** — `q0-1` · `q1-1` · `q2-1` · `q0-2` · `q1-2` · `q2-2` 를 19:32~19:58 KST 에 돌았다(Q0 판 5~6분, Q1 · Q2 판
  3~4분). khala 는 결과 문서 한 편을 판 앞에 머지해 `HEAD` 를 고정했고 picasso 는 19:10 부터 `docs/` 를 얼렸다. ⛔ 재적재는 정시 :11 이
  아니라 앞 회차가 끝나고 한 시간 뒤에 돌아(19:26~19:31, 바뀐 파일 다섯) 그 회차가 끝난 뒤 시작했다. 판 앞뒤 표지가 같았다
- [x] **셈 — 결함 하나를 판 뒤에 고침.** 첫 셈이 「결정론이 깨졌다」를 냈다. 같은 Q0 무리(R04 ≡ R10 · R06 ≡ S1 · R14 ≡ R15 ≡ R16)의 글을
  본문 해시로 견줘 사례마다 다른 자료 칸에 걸린 것이고 Q0 까지 걸렸다. 무리의 검색 열쇠와 상위 20 은 모든 판에서 같았다. 설계서 §3 의
  「구성원 글이 같다」대로 검색 열쇠를 견주게 고쳤고, 구성원의 자료 칸이 다른 줄을 기존 시험에 넣어 먼저 빨간 것을 봤다(시험 수 그대로).
  수는 고치기 전과 같고 「견줄 수 있나」만 바뀌었다. 고친 셈으로 여섯 다 성립하는 것을 본 뒤 끝 알림을 보냈다 — 다시 돈 판은 없다
